New projects ​

tiffin new makes a project in a folder of its own and serves it at <name>.test: a JavaScript stack, a blank HTML page, a Laravel app, a WordPress site or a cloned repository. Whatever it needs (Node, PHP, Composer or WP-CLI, a database server) is installed on the way. In the app, it is New project… on the Projects screen; it suggests your first parked folder.

Laravel ​

bash
tiffin new laravel shop                          # SQLite, in this folder
tiffin new laravel shop --kit vue --npm          # a starter kit, built
tiffin new laravel shop --db mariadb --php 8.4   # a database server

It runs composer create-project (of laravel/laravel, or of the starter kit: react, vue, livewire or svelte), which is what the Laravel installer does, then:

  1. writes a tiffin.toml with the project's PHP, its database server and database (unless it uses SQLite) and its site;
  2. brings it up, as tiffin up does: the server is started, the database created and shop.test served;
  3. sets APP_URL and the DB_* lines in .env, then runs php artisan migrate;
  4. with --npm, runs npm install and npm run build with Tiffin's Node.

WordPress ​

bash
tiffin new wordpress blog --title "My Blog"

It writes the tiffin.toml (PHP, MariaDB or --db mysql with a blog database, the site), brings it up, then uses WP-CLI to download WordPress, write wp-config.php and install it. The administrator is admin (--admin-user) with a random password, printed at the end, or the one you give with --admin-password. Log in at http://blog.test/wp-admin. WordPress sends no mail at install.

In the app, New project… opens a searchable gallery with all of these in one place: four tiles — JavaScript, PHP, Static HTML and Clone. The JavaScript form has a framework selector (everything in tiffin new --list) and a Node version selector with every available release; the PHP form picks Laravel or WordPress. Each section therefore takes one short form instead of overflowing the dialog with cards. Pick one, type a name and a folder, and the form shows only that choice's options. When it is done, the dialog offers Open site, Open folder and Copy URL, as well as the WordPress login card.

See it first ​

--dry-run shows what tiffin new would do, and does none of it: the runtimes it would use (installed, or downloaded first), the commands it would run, the files it would write, and the command to make the same project. --json prints the same as JSON. The WordPress password is never in it.

bash
tiffin new laravel shop --kit vue --npm --db mysql --dry-run

In the app, the New project form shows the same plan under What Tiffin will do as you change the options, with a button to copy the command. A folder that is there already shows as a warning.

JavaScript and other stacks ​

bash
tiffin new react-vite shop       # plain React, with Vite
tiffin new next blog --opt tailwind=false
tiffin new static-html landing   # a blank index.html
tiffin new --list                # every stack and its options

The stacks are React (Vite), Next.js, Vue, Nuxt, SvelteKit, Astro, Node + Express, Bun + Hono and Static HTML. tiffin new --list shows their ids and the options each takes; pass one with --opt key=value (repeat it for more than one). By default a stack uses Tiffin's installed default Node (or Bun), or downloads the newest release if none is installed; --node 22, --node 22.23.3 or --node latest chooses one. For a framework, Tiffin installs its Node (or Bun), runs the scaffolder, installs the packages, then writes a tiffin.toml with a [site] proxy to the dev server and a [processes] entry to keep it running, so shop.test has hot reload. Run tiffin up in the folder to bring it back after a restart; tiffin proc shows the dev server's state and logs. A dev server that is slow to answer is a warning: the project is still made.

Each project gets its own dev-server port. It starts with the framework's usual port (5173 for Vite, Vue and SvelteKit; 3000 for Next, Nuxt, Express and Hono; 4321 for Astro), and falls back to a free port in the 5200–5999 range when that port is already used by another project or process. The chosen port is written into the project's package.json scripts — dev and the prod script (start or preview) — so a later npm run dev (or bun run dev), or a prod run, binds exactly the port that shop.test forwards to. The [processes] dev entry runs that same script. Vite-based stacks use --strictPort: if something takes the port later, the dev server stops instead of silently moving and leaving the .test site pointing at the wrong port.

Static HTML writes an index.html and a tiffin.toml with just the site: no runtime, no dev server, nothing to install. It is served as-is, as a parked folder would be.

Clone a repository ​

bash
tiffin new clone git@github.com:acme/shop.git
tiffin new clone git@github.com:acme/shop.git --identity work --name shop-staging
tiffin new clone https://github.com/acme/shop.git --branch release

It clones into <name> (the repository's name, or --name) in the current folder (--dir), then links it as <name>.test, or brings up its tiffin.toml if it has one. A Laravel project is then set up in the background (composer install, .env, the key, npm). Git comes from Tiffin's own package on Windows and from the system elsewhere.

Over SSH, Tiffin picks the SSH identity for the host (or the one you name with --identity) and runs git with only that key. Host keys are checked strictly against Tiffin's own file: a host it has not seen is refused and its fingerprint shown, then tiffin ssh trust-host <host> --fingerprint SHA256:… once you have checked it. A key you already trust in ~/.ssh/known_hosts is carried over without asking. If the clone fails, the folder is removed.

When something fails ​

The output of each command is shown as it runs. If one fails, the folder stays as it is: delete it and try again, or fix the problem and run tiffin up in it. --dir makes the project somewhere other than the current folder; --json prints the steps and the result as JSON.
