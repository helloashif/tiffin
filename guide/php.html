PHP settings ​

Tiffin runs PHP with settings made for local development: errors shown (deprecation notices hidden; set error_reporting to -1 to see them), memory_limit 512M, uploads up to 100M, two minutes per request. Change any php.ini setting for every PHP version, or for one series:

bash
tiffin php ini                                   # what PHP runs with, and where each value comes from
tiffin php ini set memory_limit 1G               # every PHP version
tiffin php ini set max_input_vars 5000 --version 8.4   # PHP 8.4 only; wins over every version's
tiffin php ini unset memory_limit                # back to Tiffin's default

The app's PHP screen does the same: pick Every version or a series, edit a value and press Enter, or reset it.

Running PHP restarts so the next request uses the new value. The command line (php, composer, artisan) gets the same settings, except that memory_limit stays unlimited there unless you set it, as Composer advises.

A few settings are Tiffin's own and can't be changed, because sites depend on them: where mail() goes, which extensions load, and the CA bundle PHP uses for HTTPS.

Another tool's php.ini

If your shell sets PHPRC or PHP_INI_SCAN_DIR (some other PHP tools do), PHP on the command line reads that file instead of Tiffin's settings. tiffin php ini warns when it sees one; unset it in your shell's startup file. On Windows, an old PHP installer may have left an IniFilePath value under HKEY_LOCAL_MACHINE\SOFTWARE\PHP, which does the same. Sites are not affected.

Xdebug and pcov ​

Every PHP Tiffin installs has Xdebug and pcov, off until you switch them on, for every PHP version or one series:

bash
tiffin php xdebug                        # what's on, and what each PHP version has
tiffin php xdebug on                     # step debugging and Xdebug's better errors
tiffin php xdebug coverage --version 8.4 # code coverage for PHPUnit and Pest
tiffin php xdebug profile                # cachegrind profiles
tiffin php xdebug off                    # not loaded at all: no slowdown
tiffin php pcov on                       # fast code coverage instead

The app's PHP screen has the same switches, under Debugging and coverage. Sites and the command line both get them, and running PHP restarts.

Step debugging: your IDE (PhpStorm, VS Code with the PHP Debug extension) listens on port 9003. A request starts a session when it asks: XDEBUG_TRIGGER=1 php artisan ... on the command line, or the Xdebug helper extension in your browser. Change any of it like other settings, for example tiffin php ini set xdebug.start_with_request yes to debug every request, or xdebug.client_port 9000.

Profiling: with tiffin php xdebug profile, a request that asks (?XDEBUG_TRIGGER=1, a cookie of that name, or the Xdebug helper extension) is profiled, and Tiffin reads the profile for you:

bash
tiffin php profiles                      # the profiles, newest first
tiffin php profiles show <request id>    # its functions by their own time
tiffin dumps replay <id> --profile       # send a request again, profiled
tiffin php profiles clear

A profile of a request Tiffin served carries the request's id, so on the Dumps screen that request has a Profile tab: each function's own time, its time with what it called, and how often it ran. Replay with profiler sends a request again with the trigger. The cachegrind files are in Tiffin's logs folder (xdebug/), for KCachegrind or PhpStorm too.

Coverage: pcov is much faster than Xdebug's coverage mode; PHPUnit and Pest use whichever is loaded for --coverage. Tiffin won't switch both on at once, since they'd both collect it.

"has no Xdebug build"

PHP versions installed before Tiffin offered Xdebug and pcov don't have them. Remove that version and add it again (tiffin remove php 8.4.23, then tiffin add php 8.4).

Extensions ​

Each PHP has the extensions Laravel and its common packages need built in. See what each installed version has, switch the shared ones on or off, and add an extension file of your own:

bash
tiffin php ext                                     # what each PHP has: built in, shared, yours
tiffin php ext enable ldap                         # a shared one, every version
tiffin php ext disable intl --version 8.3          # one series
tiffin php ext add ~/ext/swoole.so --version 8.4   # your own file, for one series
tiffin php ext remove swoole --version 8.4         # forget a choice

For MongoDB, mongodb is a shared extension in every PHP Tiffin installs, off until tiffin php ext enable mongodb. A PHP installed before it was offered lacks it: remove that version and add it again.

The app's PHP screen has the same, under Extensions.

  • Shared extensions are the ones shipped beside PHP. On Windows that's php.net's DLLs (ldap, soap, sockets, gmp, xsl and more), with Laravel's needs on by default. Our Linux and macOS builds have everything built in.
  • Your own file (.so on Linux and macOS, .dll on Windows) must be built for that PHP series. Tiffin tries it with each installed PHP of the series first and says why if it doesn't load. A Zend extension is recognised by itself. Tiffin keeps the path, not a copy.
  • On Windows, a shared DLL is tried before it's switched on (some, such as oci8, need software of their own). DLLs your own extension needs can sit next to it for sites; for php on the command line, put them next to php.exe.

Xdebug and pcov have their own switches, above.

How many requests at once ​

Each PHP version serves 16 requests at once on Linux and macOS (php-fpm starts workers as they're needed) and 4 on Windows (php-cgi workers, started up front). Raise it for an app that calls itself, or for parallel test runs against a site:

bash
tiffin php ini set pool.workers 32               # every version
tiffin php ini set pool.workers 8 --version 8.3  # one series

pool.workers takes 1 to 256. It's Tiffin's own setting, shown with the php.ini ones, and never written into a php.ini.

Settings php-fpm can't change ​

Some settings only take effect from a php.ini (PHP calls them PHP_INI_SYSTEM, such as opcache.memory_consumption). On Linux and macOS, sites run under php-fpm, which can't change those per pool: they apply to the command line only.

Laravel queues ​

See a Laravel project's jobs without a dashboard package:

bash
tiffin php queues                 # in the project's folder, or name it
tiffin php queues retry <id|all>  # put failed jobs back on their queue
tiffin php queues forget <id>     # delete a failed job
tiffin php queues flush           # delete every failed job (asks first)
tiffin php queues clear emails    # delete what waits in a queue (asks first)

Tiffin boots the app with the project's PHP, as artisan does, and asks Laravel for the default connection's waiting jobs and the failed jobs:

  • With the database driver (a new Laravel app's), each waiting job is listed: its class, queue, attempts, and whether a worker has it now.
  • With Redis and others, how many wait in the connection's queue.
  • sync runs jobs at once, so nothing waits.

The changes run Laravel's own queue:retry, queue:forget, queue:flush and queue:clear. The app's Laravel queues tool shows the same, with buttons.
