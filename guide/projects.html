Projects: tiffin up ​

Describe what a project needs in a tiffin.toml at its root, commit it with the code, and anyone on the team brings it up with one command:

toml
[runtimes]
php = "8.4"
node = "22"

[services]
postgres = { version = "18", databases = ["shop", "shop_test"] }
valkey = "9"

[site]
name = "shop"
https = true

[processes]
queue = "php artisan queue:work"
vite = "npm run dev"
bash
tiffin up

tiffin up, in the project folder or any folder below it:

  1. installs the runtimes and services that are missing;
  2. starts the services;
  3. creates the databases;
  4. serves the site (and redirects to HTTPS, with https = true);
  5. starts the processes.

Running it again changes nothing, and needs no network once everything is installed. In the app, Add → Run tiffin.toml… on the Projects screen does the same.

Every key is described in the tiffin.toml reference. A new Laravel or WordPress project gets one from tiffin new.

Processes ​

[processes] names the commands a project keeps running: queue workers, the scheduler, dev servers. tiffind runs them in the project folder with the project's own php and node, starts a crashed one again, and stops them all when it stops.

bash
tiffin proc                  # what runs, with its state
tiffin proc start            # this project's, from its tiffin.toml (or: start queue)
tiffin proc logs queue -f    # its output
tiffin proc restart queue    # after changing code a worker has loaded
tiffin proc stop queue

The app's Services screen shows them under Project processes, with their state, restarts and logs.

A process is named <project>/<name> (shop/queue), or just by its name when only one project has it. Commands run without a shell, so &&, | and > don't work: put the steps in a script and run that. A process that crashes at once five times in a row is marked failed; tiffin proc logs says why.

On Linux and macOS a stopping process gets SIGTERM and five seconds to finish (a queue worker finishes its job). On Windows it is ended at once, with everything it started.

Workspaces ​

A workspace is a copy of the project for one git branch: its own folder, its own address and, if you want, its own database. Work on two branches at once, or let a coding agent work on one while you work on another, with no stashing and no shared database.

Say what a workspace gets in tiffin.toml (see [workspaces]):

toml
[workspaces]
database = "clone"
copy = [".env"]
env = ["APP_URL=https://{{domain}}", "DB_DATABASE={{database}}"]
after_create = ["composer install", "php artisan migrate --force"]
before_delete = ["php artisan queue:clear"]
bash
tiffin workspace new feat/checkout   # a new branch starts at HEAD; --base picks another start
tiffin workspace ls                  # branch, address, database, folder
tiffin workspace open feat/checkout  # in the browser; --in ide, terminal or files
tiffin workspace rm feat/checkout    # asks first

new shows each step as it runs: the git worktree (a folder next to the project, shop-feat-checkout), the files copied, the .env values written, the database, then your after_create commands with their output. The workspace is served at https://feat-checkout.shop.test from its own folder. If a step fails, what the earlier steps made is removed again; the branch git created stays. Running new for a branch that has a workspace changes nothing.

A cloned database is made from a snapshot of the project's; the project's own database is only read. rm runs before_delete, drops the workspace's database (never a shared one; --keep-database keeps it) and removes the folder. It refuses a folder with uncommitted changes and a failing before_delete; --force goes on anyway. The branch itself stays.

Name the project with --site or --dir; by default it is the one whose tiffin.toml is nearest to the current folder. Every command takes --json.

In the app ​

Open a project and choose Workspaces. Each workspace is listed with its address, branch, database (clone, empty or shared) and the project's health. New workspace takes a branch (and, for a new one, what it starts from) and shows each step as it happens: the folder, copied files, .env, the database and your after_create commands. Open the site or the folder from a row. Remove says what goes (the before_delete hook runs, the database if the workspace has its own, the folder, the address) and that the git branch stays; a folder with uncommitted changes asks again before it is forced. Each workspace also appears under its project in the sidebar. This replaces the old Worktrees tool, and old links to it open the project's Workspaces tab.

Projects at a glance ​

Every site is a project. tiffin project lists them with their health in four layers, the same ones the app draws as a stack:

  • web: the site is served (or why not).
  • runtime: the PHP version requests run with, and what tiffin.toml pins.
  • services: what [services] asks for is running.
  • processes: its [processes] are running; off until tiffin up.
bash
tiffin project              # every project, one line each
tiffin project info shop    # layers with reasons, pins, services, processes, ports
tiffin project pin shop     # pin a project so it appears first in Projects and on Overview
tiffin project unpin shop   # remove the pin
tiffin project ls --json

In the app ​

The same four layers are the carrier drawn for each project on Overview, in the Projects list and at the top of a project. Each stripe is green (ok), amber (warn), red (bad) or grey (off, for example processes before tiffin up); a project's state is its worst layer. On Projects, you can sort by Name, PHP, Node, Path, or Date added (ascending or descending) and pin favourite projects with the pin button or ⋯ menu; pinned projects stay at the top of Projects and appear in their own Pinned section above Recent on Overview. Click a project for its tabs: Overview (the latest request as a waterfall, each route's p95, the processes), Workspaces, Insights and Changes (AI preview). Run tiffin.toml… in the Add menu runs tiffin up in a sheet that shows each step. The app has the details.

For the numbers behind the carriers, in a terminal: tiffin stats (requests, 5xx and p95 per site, or a site's routes over a day) and tiffin top (CPU and memory of tiffind, its services and your processes, sampled every 5 seconds for an hour). Both take --json.

Checking a project ​

tiffin check compares what a project asks for with what Tiffin has for its folder, and says how to fix each difference. It changes nothing. tiffin check --fix makes the fixes that Tiffin can do by itself, then checks again.

bash
tiffin check            # the project in this folder
tiffin check ~/Sites/shop
ChecksAgainst
composer.json's phpthe PHP this folder runs (tiffin use, tiffin.toml or the default)
composer.json's ext-*that PHP's extensions, and whether each is on
.env.env.example's variables, and an empty APP_KEY
.env's service settingswhat Tiffin runs (tiffin env)
package.json's engines.nodethe Node this folder runs
text
Checking shop.test (/home/ada/Sites/shop)
FAIL  composer.json asks for PHP >=8.1 <8.4; this folder runs 8.4.23
      fix: tiffin use shop 8.3
FAIL  composer.json needs ext-redis; PHP 8.4.23 doesn't have it
      fix: tiffin php ext add <its .so or .dll> --version 8.4
warn  DB_PORT is "3306" in .env; Tiffin's is "5432" (Database)
      fix: tiffin env (the lines to paste)
ok    Node 22.11.0 meets package.json's >=20

It exits 1 when a check fails, so it fits a script.

Fixing what it finds ​

bash
tiffin check --fix               # every fix Tiffin can do by itself
tiffin check --fix --only env    # only .env and APP_KEY

--fix shows each fix and its output as it runs, then prints the new check. These are the fixes it makes:

FindingWhat --fix does
No PHP or Node, or none that fitsinstalls the lowest version allowed
The site runs a PHP that doesn't fitswitches the site to one that fits (tiffin use), installing it first if needed
An extension that is offturns it on for that PHP
No .envcopies .env.example, then sets APP_KEY in a Laravel project
An empty APP_KEYruns php artisan key:generate
.env lacks variablesadds them, as .env.example writes them, at the end of .env

--fix never changes your .env's own lines, and makes these fixes only when you ask:

  • the service settings: tiffin env prints the lines to paste
  • pinning a version in tiffin.toml
  • adding an extension from a file

A fix that fails doesn't stop the others. --fix exits 1 if a fix failed or a check still fails.

In the app, choose Check project… in a site's ⋯ menu on Projects. It shows the same findings, each with its fix to copy. A finding Tiffin can fix also gets a Fix button, and Fix all fixes every one of them. The steps and their output show while the fixes run.
