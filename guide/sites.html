Sites ​

A site is a folder served at https://<name>.test. Tiffin finds the web root itself:

  • Laravel and Symfony serve public/, Magento pub/, CakePHP webroot/ (even before their index.php exists, so a half-cloned project never exposes its .env);
  • otherwise the folder's own index.php, then the first of web/, public/, webroot/ or pub/ with an index.php, then index.html.

Park a folder ​

Every subfolder of a parked folder is a site, named after it:

bash
tiffin park ~/Sites        # ~/Sites/shop -> shop.test
tiffin parked              # the parked folders
tiffin unpark ~/Sites

New projects in a parked folder are served at once.

A parked folder on a network share or a drive that goes to sleep can stop answering. Tiffin gives each parked folder 2 seconds to list its projects. If one doesn't answer in time, the other folders' sites go on being served, and that folder's sites are listed as they last were but not served until it answers again. tiffin sites says which folder isn't answering.

Link one folder ​

bash
tiffin link                # this folder, named after it
tiffin link shop           # this folder, as shop.test
tiffin link shop ../api    # that folder, as shop.test
tiffin unlink shop

A linked name wins over a parked folder of the same name.

See your sites ​

bash
tiffin sites

It lists every site with its address, PHP version and folder, and the folders that are not served and why.

Web root ​

Tiffin detects the folder to serve: public/ for Laravel and Symfony, the project folder for WordPress, web/ for Drupal, and so on (tiffin sites shows it and why). To choose another:

bash
tiffin root shop dist        # serve shop/dist
tiffin root shop .           # the project folder itself
tiffin root shop auto        # detect it again

It has to be a folder inside the project. A project can set it in tiffin.toml ([site] root = "dist"), and the app has Change web root… in a site's ⋯ menu. If the chosen folder disappears, the site isn't served (rather than serving the whole project, .env and all) until it's back or you go back to auto.

Routing rules ​

Unknown paths go to the web root's index.php (your framework's router), or to its index.html when there's no index.php. A rule sends the paths under a prefix somewhere else, when no real file or folder matches:

bash
tiffin route add portal /api api/index.php   # a nested app's front controller
tiffin route add dashboard / index.html      # a single-page app's deep links
tiffin route list
tiffin route remove portal /api

Real files always win, and the longest prefix applies (/api covers /api/users, not /apix). A PHP target gets every method and the original URI; a page answers GET and HEAD only. A project can list rules in tiffin.toml under [site.routes], and the app has Routing rules… in a site's ⋯ menu.

With a catch-all to index.html, a missing script or stylesheet gets the page instead of a 404, as with nginx's try_files. If the browser reports a syntax error in a script, check that the asset was built.

Subdomains ​

Every name under a site is that site too: api.shop.test, tenant1.shop.test and a.b.shop.test all serve shop, over HTTPS as well. Your app sees the name asked for ($request->getHost()), so Laravel's subdomain routes and multi-tenant apps work as they would in production:

php
Route::domain('{tenant}.shop.test')->group(function () {
    // ...
});

tiffin secure redirects a subdomain to https:// at the same name.

Aliases ​

Give a site more names: each alias serves it too, with the names under it.

bash
tiffin alias shop store      # store.test (and api.store.test) serve shop
tiffin alias admin           # in the project's folder: for its site
tiffin unalias store
tiffin sites                 # aliases are in the ALSO column

A project's tiffin.toml can ask for them ([site] aliases = ["store"], applied by tiffin up), and the app's Projects screen shows them, with Add alias… in a site's ⋯ menu. An alias stays with the project folder. It can't be another site's name, and a site created later with that name wins over it.

Proxies ​

Give a server on this computer a .test name: Vite's dev server, Reverb, a Node or Go app. It answers over http:// and https:// with Tiffin's certificate, websockets included:

bash
tiffin proxy vite 5173                  # vite.test forwards to http://127.0.0.1:5173
tiffin proxy api http://localhost:3000
tiffin unproxy vite

The server sees its own address as Host, and the .test name in X-Forwarded-Host. Targets must be on this computer (127.0.0.1, localhost or [::1]). In the app, it is Add → Proxy a port… on the Projects screen.

For Vite's hot reload over HTTPS, point its HMR at the proxy in vite.config.js:

js
server: { hmr: { host: 'vite.test', protocol: 'wss', clientPort: 443 } }

HTTPS ​

Every site already answers on https://, with a certificate from Tiffin's own certificate authority (trusted by tiffin elevate). tiffin secure also redirects http:// to https://:

bash
tiffin secure shop         # or, in its folder: tiffin secure
tiffin unsecure shop

PHP per site ​

A site runs the PHP version its tiffin.toml asks for, else the global default. To choose one for a site:

bash
tiffin use shop 8.3        # shop.test runs PHP 8.3
tiffin use shop default    # back to tiffin.toml or the global default

The php and composer commands in its folder follow the same choice.

Compression and file downloads ​

  • Text is sent gzipped to browsers that ask for it: HTML, CSS, JavaScript, JSON, XML and SVG of 1 KB or more, from PHP and from the web root alike. Pictures, fonts, ranges and event streams are sent as they are, and so is a response your app already encoded.
  • Your app can hand a file to Tiffin to send, as it would to Apache or nginx. Answer with an X-Sendfile header naming the file's full path, or nginx's X-Accel-Redirect with a path from the project's folder (/storage/app/report.pdf). Tiffin sends that file instead of PHP's body, with ranges and caching, and keeps your other headers (Content-Type, Content-Disposition). PHP's worker is free again while the file goes out. The file must be inside the project's folder, links followed; anything else gets a 403.

Before tiffin elevate ​

.test names don't resolve until the system is set up, and on Linux ports 80 and 443 need it too: sites are then on 127.0.0.1:8080 and 8443. (macOS and Windows use 80 and 443 at once, unless another program has them. On macOS tiffind listens on every address for this, since a program without root may not bind a low port on loopback alone, and turns away every connection that doesn't come from this computer.) Subdomains need the resolver tiffin elevate sets up: a hosts file can't list every name under a site. Meanwhile open http://localhost/~shop.test/ (or localhost:8080 on Linux) to pin your browser to a site; /~ unpins.
